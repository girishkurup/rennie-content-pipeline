Rennie Content Pipeline — Architecture

A human-in-the-loop AI content pipeline on AWS: three Bedrock AgentCore agents, a Step Functions state machine, and a React frontend, wired together with Terraform.

By layer

What each piece actually does, and the non-obvious parts worth knowing.

Frontend & auth

  • React + Vite + TypeScript SPA, hosted on S3 behind CloudFront (Origin Access Control, no public bucket)
  • Cognito Hosted UI, Authorization Code + PKCE, via react-oidc-context
  • Two groups: requesters (submit briefs) and reviewers (approve/reject) — enforced inside each Lambda by reading the cognito:groups claim, not at the API Gateway layer
  • CloudFront custom error responses (403/404 → index.html) make client-side routing work on direct URL loads

API

  • API Gateway HTTP API (not REST) with a native Cognito JWT authorizer
  • chat_handler — creates the job, kicks off the pipeline
  • history_handler — reads conversations/jobs, issues presigned S3 download URLs
  • review_handler — resumes a paused execution (approve/reject) or stops one outright

Orchestration

  • One Step Functions Standard execution per job, named after the job_id
  • PrepareHumanReview pauses the whole execution (waitForTaskToken) until a human acts — no polling, no timeout pressure
  • Rejections loop back through ReviseDraft up to max_human_review_iterations, then auto-escalate
  • A Catch on the Lambda tasks routes real failures to MarkFailed instead of leaving a job silently stuck

Agents

  • Three independently-deployed Bedrock AgentCore Runtime containers (Strands Agents SDK, ARM64), each its own ECR repo and IAM execution role
  • Orchestrator calls Writer and Reviewer directly via bedrock-agentcore:InvokeAgentRuntime — both an identity policy on the caller and a resource policy on the callee are required
  • Orchestrator's fetch_url tool actually crawls a given reference URL and grounds the draft in it, when one is supplied
  • Orchestrator returns clean structured fields (captured straight from its tool calls) rather than parsing the model's own narration
  • Orchestrator writes a live current_step string to content_jobs before every Writer/Reviewer/fetch_url call — "Writer agent is drafting (round 2 of 3)…" — best-effort, polled by the frontend so a 150-300s run isn't a frozen screen

Data

  • DynamoDB, pay-per-request: conversations, messages, content_jobs (with by_status / by_conversation GSIs)
  • content_jobs is the single source of truth the whole UI reads — status, current_step, every draft stage, review counters, the Step Functions execution ARN
  • S3 mirrors every draft version as its own object — an audit trail DynamoDB's overwrite-in-place fields don't keep

Resilience (learned the hard way)

  • Every Bedrock model call and every InvokeAgentRuntime call uses adaptive-mode retry — under concurrent test load, the account's on-demand Bedrock throttling was routine, not exceptional, and used to crash a Runtime invocation outright (500)
  • Every InvokeAgentRuntime caller sets an extended read_timeout — boto3's 60s default was silently killing every real Orchestrator call client-side, since that call blocks with zero bytes until the whole 150-300s draft/review loop finishes
  • A failed sub-call no longer burns one of the Orchestrator's 3 AI-review rounds — an infra hiccup isn't a real review
  • pipeline_task_writer's own Lambda timeout (480s) stays the ultimate ceiling under all of the above, so a genuine hang still reaches Step Functions' Catch → MarkFailed instead of hanging forever

Not always running

  • Knowledge Base (OpenSearch Serverless + Bedrock KB) — built, tested end to end, then torn down; stands up only for a deliberate one-off test
  • Everything else here is pay-per-use or idle-free (DynamoDB on-demand, Lambda, Step Functions, AgentCore Runtime) — OpenSearch Serverless is the one component that bills while idle

Frontend → Orchestrator: the full call chain

Every hop a request takes from clicking "Save & Generate Content" to actually reaching the Orchestrator's AgentCore Runtime endpoint.

HopWhat happensConfiguration
1 Browser calls the API fetch(`${VITE_API_ENDPOINT}/chat`) with Authorization: Bearer <id_token>, from frontend/src/api.ts. VITE_API_ENDPOINT is baked in at build time via frontend/.env.production.
2 API Gateway authenticates + routes HTTP API route POST /chat. A native JWT authorizer checks the token's issuer (https://cognito-idp.<region>.amazonaws.com/<user_pool_id>) and audience (the app client ID) before the request ever reaches Lambda.
3 Lambda proxy integration AWS_PROXY integration, payload format 2.0, target chat_handler. A matching aws_lambda_permission is what actually lets API Gateway invoke it.
4 chat_handler starts the pipeline Writes the job to DynamoDB (status: queued), then stepfunctions:StartExecution on content-pipeline with {job_id, brief} as input — execution name = job_id.
5 State machine invokes a Lambda task First state ProduceInitialDraft runs pipeline_task_writer with mode: "initial".
6 pipeline_task_writer calls the Orchestrator boto3.client("bedrock-agentcore").invoke_agent_runtime(agentRuntimeArn=ORCHESTRATOR_RUNTIME_ARN, payload={"brief", "job_id"}) — synchronous, blocks until the whole draft/review loop returns (read_timeout=470 to survive that).
7 IAM double-check Requires both: an identity policy on pipeline-task-writer-exec allowing InvokeAgentRuntime on the Orchestrator's runtime ARN and its /runtime-endpoint/* sub-resource, and a resource policy on the Orchestrator's runtime naming that same role as an allowed principal.
8 Request lands on the endpoint Physically resolves to <orchestrator_runtime_arn>/runtime-endpoint/DEFAULT — the Orchestrator container's @app.entrypoint (BedrockAgentCoreApp, HTTP protocol) receives the payload and takes it from there.

One request, start to finish

What actually happens between clicking "Save & Generate Content" and a final, approved draft.

  1. Submit. chat_handler writes the conversation, the message, and a new content_jobs row (status: queued), then starts the Step Functions execution. One execution per job — it lives for the job's entire lifetime, including every later revision.
  2. AI draft + AI review. pipeline_task_writer invokes the Orchestrator, which optionally fetches a reference URL, calls the Writer for a first draft, then the Reviewer for a critique — looping revise↔review up to a capped number of AI rounds. Both the raw first draft and the post-AI-review draft are saved separately, to DynamoDB and S3. The requester's own page shows which of these is happening live, via the Orchestrator's current_step writes.
  3. Hand off to a human. The execution reaches PrepareHumanReview and genuinely pauses — the task token is stored on the job, and nothing runs again until a reviewer acts. This is where the job sits at status: pending_human_review, visible on the requester's own page.
  4. A reviewer decides. Approve resumes the execution straight to FinalizeApproved. Reject-with-feedback sends that feedback to the Writer for a direct revision (no AI review loop this time), and the job returns to step 3. Past the configured cap, a rejection escalates instead of looping again.
  5. Finalize. pipeline_finalize writes the final draft to DynamoDB and S3 and sets a terminal status — completed, escalated, stopped, or failed. A requester or reviewer can also call /stop at any point in flight, which cancels the execution directly.
Note — this reflects the system as actually deployed and tested against real AWS, not a plan: every arrow above has been exercised end to end at least once, including two real production failure modes (Bedrock throttling crashing a Runtime call, and a client-side read timeout killing every job before human review) that were root-caused from live CloudWatch/Step-Functions state and fixed, not assumed.
