# Deploying this repo to a new AWS account

This repo has no account-specific values baked into it — every ARN and
resource name is computed from `data.aws_caller_identity` / `data.aws_region`
at apply time, not hardcoded. Deploying to a different account is mostly
"point your credentials at the new account and run the same commands," not a
code change. This doc is the exact procedure, including the handful of steps
that genuinely can't be config-file-driven (AWS platform constraints, not
gaps in this repo).

## Prerequisites

- AWS credentials for the **target** account active in your shell (`aws sts
  get-caller-identity` to confirm — every command below acts on whatever
  account your credentials currently point at, there's no account-switching
  flag in any script here).
- Terraform >= 1.9.0, Docker Desktop (with `buildx`, ships by default),
  Node.js (for the frontend build).
- **Bedrock model access enabled in the console** — this is an AWS
  account+region-level manual approval with no Terraform resource or CLI
  equivalent. Bedrock console → Model access → enable the models named in
  `terraform/envs/dev/dev.tfvars` (`bedrock_writer_model_id`,
  `bedrock_reviewer_model_id`, `bedrock_orchestrator_model_id`,
  `bedrock_embedding_model_id`). `terraform apply` will fail at the
  AgentCore Runtime step if this is skipped.

## Files your engineer actually needs to touch

| File | What to change | Required? |
|---|---|---|
| `terraform/envs/dev/dev.tfvars` | `aws_region` (only if not us-east-1 — see the cross-region note below), `alert_email` if you want it wired up (see "Known gaps"), `project_name`/`environment` if you want different resource names. `agent_image_tag` gets bumped **for you** by `scripts/deploy_agents.sh` — don't hand-edit it. | **Yes** — review it even if nothing needs changing. |
| `frontend/.env.production`, `frontend/.env.development` | Nothing — generated by `scripts/generate_frontend_env.sh`. | No (don't hand-edit; get overwritten) |
| Everything else | Nothing. Account ID, all ARNs, ECR URIs, IAM policies, the CloudFront domain fed into Cognito's callback URLs — all computed from Terraform data sources, not hardcoded. | No |

That's it — **one file to review** (`dev.tfvars`), and it often needs zero
edits if you're deploying the same region with the same models.

### Cross-region note

`bedrock_writer_model_id` etc. currently use a `us.*` cross-region inference
profile ID. Deploying outside the US requires swapping these for the
matching regional profile (e.g. an `eu.*` prefix) — check Bedrock model
availability in the target region first, not every model/region combination
is supported.

## Deploy procedure

```bash
# 1. Clone and review dev.tfvars (see table above)
git clone <this-repo> && cd <this-repo>

# 2. First-time only: create the ECR repos before anything else, since the
#    AgentCore Runtime resource validates the image exists at apply time —
#    see the comment at the top of terraform/modules/agentcore_runtime/runtime.tf
cd terraform/envs/dev
terraform init
terraform apply -var-file=dev.tfvars \
  -target=module.writer_agent.aws_ecr_repository.this \
  -target=module.reviewer_agent.aws_ecr_repository.this \
  -target=module.orchestrator_agent.aws_ecr_repository.this
cd ../../..

# 3. Build and push the three agent images, bumps agent_image_tag for you
./scripts/deploy_agents.sh

# 4. Full apply — creates everything else (Cognito, DynamoDB, API Gateway,
#    Step Functions, the AgentCore Runtimes themselves, S3+CloudFront)
cd terraform/envs/dev && terraform apply -var-file=dev.tfvars && cd ../../..

# 5. Generate the frontend's env files from the outputs step 4 just created
./scripts/generate_frontend_env.sh

# 6. Build and upload the frontend (terraform manages the S3 upload itself
#    via fileset() — see terraform/modules/frontend_hosting/deploy.tf)
cd frontend && npm install && npm run build && cd ..
cd terraform/envs/dev && terraform apply -var-file=dev.tfvars && cd ../../..

# 7. Invalidate CloudFront so the new frontend build is actually served
aws cloudfront create-invalidation \
  --distribution-id "$(cd terraform/envs/dev && terraform output -raw cloudfront_distribution_id)" \
  --paths "/*"
```

## Redeploying after a change (not a fresh account)

- **Agent code changed** (`agents/*/agent.py`): `./scripts/deploy_agents.sh`
  then `terraform apply` in `terraform/envs/dev`.
- **Lambda code changed** (`lambdas/*/handler.py`): just `terraform apply` —
  Terraform hashes the zip (`data.archive_file`) and redeploys automatically,
  no separate build step.
- **Frontend changed**: `npm run build` in `frontend/`, then `terraform
  apply`, then the CloudFront invalidation command from step 7.
- **Infra changed** (any `.tf` file): `terraform apply`.

## Known gaps — not automated by anything in this repo

- **The test Cognito user** (`testuser@example.com` in the original deploy)
  is not Terraform-managed — it was created ad hoc via `aws cognito-idp
  admin-create-user` + `admin-set-user-password` (deliberately: putting a
  password in Terraform state is a bad idea). Create your own via the same
  two commands, or through the Cognito console, and add them to the
  `requesters` and/or `reviewers` group.
- **`alert_email`** (`dev.tfvars`) is declared but not currently wired to
  any SNS topic or CloudWatch alarm — setting it today does nothing. Worth
  fixing before relying on it.
- **AWS Budget alert** — set up manually via the console/CLI in the original
  account, not IaC-managed. Recreate it per account if you want the same
  spend guardrail.
- **Knowledge Base / OpenSearch Serverless** (`terraform/modules/
  knowledge_base`) — built and tested once, then deliberately left
  commented out of `terraform/envs/dev/main.tf`, since OpenSearch Serverless
  bills continuously even idle. Only uncomment it for a deliberate,
  time-boxed test, then comment it back out and `terraform apply` to tear it
  down.
- **Remote state** — this repo uses local Terraform state (see the
  commented-out `backend "s3"` block in `terraform/envs/dev/providers.tf`).
  Fine for one engineer; for a team, stand up an S3 bucket + DynamoDB lock
  table per account and run `terraform init -backend-config=...` (or
  uncomment and fill in that block) before the first apply.

## Verifying the deployment

```bash
cd terraform/envs/dev
terraform output   # frontend_url, api_endpoint, cognito_* — sanity-check these resolve
```

Then open `frontend_url` in a browser, sign in with the test user, and
submit a Web Article request — it should reach `pending_human_review` within
a few minutes (watch `current_step` on the job page for live progress).
